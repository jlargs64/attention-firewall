## Purpose

Owns the user's data: one isolated context per machine environment, an append-only JSONL event log that is the only source of truth, and plain-file export that needs no `fw` to read.

## ADDED Requirements

### Requirement: Context initialization
`fw init` SHALL create a context directory containing an empty event log and SHALL append a `context_created` event carrying `slot_cap` (integer, default 3) and `stall_after_days` (integer, default 7). The context path SHALL default to `$XDG_DATA_HOME/fw` (falling back to `~/.local/share/fw`) and SHALL be overridable by `--context PATH` or the `FW_CONTEXT` environment variable. `fw init` SHALL require no network access and no credentials.

#### Scenario: First init
- **WHEN** `fw init` runs and no context exists at the resolved path
- **THEN** the directory and `events.jsonl` are created, the first line is a `context_created` event with `slot_cap: 3` and `stall_after_days: 7`, and the exit code is 0

#### Scenario: Init with custom cap
- **WHEN** `fw init --slots 2 --stall-days 10` runs
- **THEN** the `context_created` event records `slot_cap: 2` and `stall_after_days: 10`

#### Scenario: Init on existing context
- **WHEN** `fw init` runs and `events.jsonl` already exists at the resolved path
- **THEN** nothing is written, an error names the existing path, and the exit code is 3

#### Scenario: Command before init
- **WHEN** any command other than `init`, `--version`, or `--help` runs and no context exists at the resolved path
- **THEN** the command writes nothing, reports that the context is not initialized, and exits with code 4

### Requirement: Append-only event log
Every state-changing operation SHALL append exactly one JSON object per line to `events.jsonl` and SHALL never rewrite or delete an existing line. Each event SHALL carry: `seq` (integer, strictly increasing from 1), `ts` (ISO 8601 UTC timestamp), `actor` (string, one of `human`, `agent:<name>`, or `system`), and `kind` (string, one of `context_created`, `config_changed`, `mission_created`, `item_created`, `item_mapped`, `item_transitioned`). Kind-specific fields SHALL be as defined by the `bandwidth-graph` capability.

#### Scenario: Append preserves prior lines
- **WHEN** a command succeeds against a log with N lines
- **THEN** the log has N+1 lines and the first N lines are byte-identical to before

#### Scenario: Refused operation writes nothing
- **WHEN** a command is refused by a graph rule or fails validation
- **THEN** the log is unchanged

#### Scenario: Sequence numbers are contiguous
- **WHEN** the log is read
- **THEN** `seq` values are 1, 2, 3, ... with no gaps or repeats

### Requirement: Actor recorded on every event
The `actor` field SHALL be `human` unless the invocation supplies `--actor agent:<name>` or the `FW_ACTOR` environment variable, in which case it SHALL be that value. Events generated by the tool's own arithmetic (stall detection) SHALL carry `actor: system`. An `agent:<name>` actor on an event means the agent acted on its own with the human's standing permission; the log makes that visible but does not enforce it.

#### Scenario: Default actor
- **WHEN** `fw add "write the spec"` runs with no actor option or variable
- **THEN** the `item_created` event has `actor: human`

#### Scenario: Agent actor
- **WHEN** `fw add "write the spec" --actor agent:claude` runs
- **THEN** the `item_created` event has `actor: agent:claude`

#### Scenario: Invalid actor
- **WHEN** a command runs with `--actor robot`
- **THEN** the command is refused as a usage error with exit code 2 and nothing is written

### Requirement: Ledger content is untrusted
On every read the tool SHALL parse each line against the event schema. A line that is not valid JSON, lacks a required field, has a field of the wrong type, breaks the `seq` sequence, or names an unknown `kind` SHALL cause the command to stop before writing anything, report the offending line number, and exit with code 5. The tool SHALL never repair, skip, or rewrite a malformed line.

#### Scenario: Malformed line
- **WHEN** line 7 of `events.jsonl` is `{"seq": 7, "kind": "item_created"` (truncated)
- **THEN** any command reports line 7 as malformed, writes nothing, and exits with code 5

#### Scenario: Unknown event kind
- **WHEN** a line has `kind: "teleport"`
- **THEN** the command reports the line number, writes nothing, and exits with code 5

### Requirement: Export to plain files
`fw export --format jsonl|csv --out PATH` SHALL write the ledger in a form that needs no `fw` to read. JSONL export SHALL be a byte-identical copy of `events.jsonl`. CSV export SHALL contain one row per item with columns `id`, `title`, `mission`, `state`, `created`, `last_event`, `until`, `overrides`. Export SHALL append no event and SHALL write nothing inside the context directory.

#### Scenario: JSONL export
- **WHEN** `fw export --format jsonl --out /tmp/fw.jsonl` runs
- **THEN** the output file is byte-identical to `events.jsonl` and the log is unchanged

#### Scenario: CSV export
- **WHEN** `fw export --format csv --out /tmp/fw.csv` runs against a context with 3 items
- **THEN** the file has a header row and 3 data rows with the listed columns

### Requirement: Context isolation
No command SHALL read from or write to any path outside the resolved context directory except the explicit `--out` target of `export`. There SHALL be no code path that reads a second context.

#### Scenario: Two contexts on one machine
- **WHEN** `FW_CONTEXT=/a fw add "x"` and `FW_CONTEXT=/b fw status` run
- **THEN** the status output from `/b` does not include the item created in `/a`
